Scheduler

the book of jobs · door on :8132 · one slot · runner dummy or local

The Scheduler is the only place on a node that decides when work happens. A caller submits a job — one service with its inputs, or a graph of steps that waits on its own predecessors — and gets an id back while the job is still queued. The book admits one job at a time, records what each one asked for, runs it through a runner seam, and publishes the queued and running jobs to State so the rest of the LAN can see the node is busy without asking it anything.

How it holds together

A job is a graph, never a list. Every job carries steps[], and a flat {service, inputs} submit becomes the degenerate one-step DAG (id: "s1") through fromLegacyJob(). That costs nothing today and avoids a record migration the first time a video needs an image and a voice. A step declares:

fieldmeaning
idunique in the job — a name like s1, at most 32 chars of letters, digits, ._- — the handle needs and {{id.key}} refer to
servicea name from the catalog, never a node path
valuesthat service's declared inputs, possibly carrying {{s1.image}} tokens
needsincoming edges — these steps must be done before this one may start
produces · outputartifact names, and the real path or value behind each name once it ran
nodewhere it must run; absent means this node. A step naming another node is refused by the local runner as remote_node_not_wired

The graph is validated before the job is booked. validateGraph() refuses empty_graph, bad_step_id, duplicate_step, bad_needs, unknown_dep and cycle, and every refusal names the offending refs (cycle: s1 -> s2 -> s1, not "invalid graph"). The cycle check is not pedantry: with one slot, a cycle would sit forever and look exactly like nothing happening. topoOrder() is Kahn's algorithm, and its unordered remainder is the named cycle.

Tokens resolve from what actually happened. {{s1.image}} is substituted at run time from the producing step's recorded output map — never from a filename convention. If no step produced the key, the token stays and the step fails with unresolved_token; the runner would rather stop than pass a template string to a model.

One slot is the rule of the box, not a limitation. pump() admits nothing while something runs, then takes the oldest queued job, marks it running, persists, awaits the runner, and records done or failed. concurrency defaults to 1 and the seam allows more (--concurrency), but the machine's law is one GPU, one job. A submit returns before any work starts: the job is pushed, the book is persisted, the pump is scheduled on a microtask, and the caller receives a copy (snap()) so it never watches a status change under its own hands.

Statuses mean what they say. queued | running | done | failed | cancelled. On boot the book is reloaded and any job the file still calls running is loaded as failed with the sentence "the door restarted while this job was running — it did not finish", and its steps are demoted the same way. A file cannot claim work that stopped when the process did.

Cancel means cancel — a queued job leaves the queue, a running one is refused. POST /api/jobs/:id/cancel answers 200 when a queued job is cancelled, 409 with the job and the reason when it is already running ("a running job is not killed from here"), and 404 for an unknown id. Lying about a kill would be worse than admitting the limit.

The runner is a seam, and today's seam says so. Runner is { kind, description, run(job) }. The shipped default is createDummyRunner(): it sleeps 1200 ms, writes the job as done, and returns executed: false with a note naming the service and its input keys — so the wiring (submit · queue · run · status · publish) is real while nothing is executed. --runner local (SCHEDULER_RUNNER=local) swaps in createLocalRunner(), which for each ready step does three things:

stagewhat it does
residencyif the service is server-shaped (gui.kind === 'command'), make that model the resident one: evict only when the card is actually tight, then wait for the old port to stop answering (a kill returns long before the port frees), start through ProcessWrapper tagged basic-gui, and wait for /health
invokeserver-shaped → its own POST /v1/chat/completions; run-per-job → Basic_App's /api/basic/run, then read the artifact from the process output line WROTE <path>
recordattach the artifact into the job's own folder as <stepId>-<basename> (hard link first, copy as fallback); an answer with no file is still written as <stepId>-answer.txt

Two of its refusals are deliberate: a run that names no file is no_artifact rather than "done", and unknown free VRAM is not permission to kill someone else's model — it shares the box and lets a failed start be honest. Delivery (deliver.mode = auto · link · copy) reports which mode actually worked, because "linked" and "copied" are different claims and a pointer file is neither.

The book is published, because a booking nobody can see is a private note. Every 5 s (SCHEDULER_PUBLISH_MS) the publisher writes to State:

entrycontentwhen
node.<ref>.scheduler.booked.<jobId>{id, service, state, at, created, keys[], graph} — inputs as their keys only, never their valueswhile the job is queued or running
node.<ref>.scheduler{at, queued, running, done, failed, cancelled, total, booked, nextAt}every tick

Finished jobs are not published individually — only the summary counts — so a long-lived node does not grow the LAN's state without bound. A job that leaves the book is dropped by name (POST /api/state/drop). The publisher's HTTP calls have a 700 ms timeout and return false instead of throwing: a State that is down logs a line and the book keeps turning. ref comes from Core/data/node.json, then Menu/data/node.json, then the literal scheduler; SCHEDULER_REF overrides.

What is not wired. This module does not call the ResourceManager — no reference to :8129 exists in its sources — so a job is booked into the Scheduler's book without a corresponding resource booking. The resource booking today comes from Basic_App. The two books are adjacent, not joined.

One more fact worth stating plainly: the Scheduler door carries no token — /api/* and /mcp are open to whoever can reach the port, which defaults to 127.0.0.1. Its own gate is public/ts/selftest.ts, 51 cases covering the queue's semantics, the HTTP surface and the pure publish step.

This is wiring in words, not a type. The shapes live in public/ts/scheduler.ts, graph.ts, publish.ts, runner-local.ts and apiServer.ts; if this page and those files disagree, the files are right and this page is a bug.
