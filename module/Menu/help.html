Menu

the way in · door on :8133 · the tree of what this node can make, the LAN underneath it

Menu is the page a person opens to find out what this box can make and to ask for one of it. It draws one row per service from the Services catalog, shows that service's own advert beside the row, opens its inputs page on click, and turns the filled form into a single booking on the Scheduler. It starts nothing, stores nothing, and copies no description: the words a row shows are the words the service file already says.

How it holds together

The tree is a view, not a copy. Every read goes out to Services (:8128): GET /api/services gives the list, then one GET /api/services/<name> per row gives the task, the declared variables.input fields, the models and the advert. The rows are kept for 2000 ms (cacheMs) so a hover-swap does not re-read the catalog four times, and /api/menu?fresh=1 exists for a caller who refuses the cache. A service file edited on disk therefore changes the tree without touching Menu.

A refusal is drawn, not hidden. When the catalog marks a row ok: false, Menu still lists it — labelled Refused, with ⛔ — and refuses to open its advert or inputs. A broken service file is news; a missing row would be silence, and silence is what the catalog exists to prevent.

One origin, so the browser never hears about three ports. The page loads only from :8133. Adverts and inputs are fetched by the door from /api/services/<name>/ad and /api/services/<name>/inputs, then wrapped in Menu's own chrome and framed with ?embed=1. Booking, reading and cancelling all go through the same door. There is no CORS anywhere in this design because there is only one origin.

Booking is a relay, not a run. POST /api/run forwards its body to the Scheduler's POST /api/jobs; GET /api/jobs, GET /api/jobs/<id> and POST /api/jobs/<id>/cancel are passed through unchanged. Every upstream call is bounded at eight seconds, and a dead Scheduler comes back as 502 with {error:{code:"upstream_down"}} rather than a hung request — the failure is the answer. This is also why /health never asks upstream anything: it reports what the door is (its URLs, the last catalog counts, or "not read yet"), not how fast someone else is.

The LAN is a second, separate read — and it comes from the browser. Beneath the tree, one script does a single fetch('http://127.0.0.1:8137/api/lan.json') every 5 s, straight to Mirror, and renders nodes[] minus role === 'self': each peer's verdict, cycle, misses, degraded flag and age, its services (ready, karma), and what it has booked. Peer services arrive as {slug, name, provider, karma, ready, modes}; booked jobs as {id, service, at, state}. Absence is drawn as absence: no peers means the section is hidden, an unanswered Mirror means the section says "the Mirror door (8137) is not answering" — never a stale list. This node's own services are the tree above, not this list.

The page follows its own file. GET /api/page-version returns <size>-<mtime> for public/index.html; the page polls it every 4 s and reloads itself when the stamp moves. Editing the page is a file edit — no esbuild, no tsc, no door restart. The door reads index.html from disk on every GET / for the same reason.

What a service needs from the machine is instance data. data/node.json holds name, ref, gpu, modelsDir and per-service modelsDirs. Only /api/models/<name> reads it, and only to find where a declared weights file sits on this box — so the same service file can run on another node unchanged. Sizes seen last time are cached in data/models-cache.json, which is why the model pane can draw before the disk answers, and why it then corrects itself with ?verify=1.
