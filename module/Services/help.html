Services

the catalog · door on :8128 · definitions only — nothing here runs

Services is the list of things this node could be asked to do, written down instead of executed. It scans one folder of .js files — each file one service, loaded as data and validated against a schema — and serves the result as a listing of shapes, a whole definition by name, and the two pages every service carries: the ad that sells it and the inputs that gather what a run needs. It declares; it never runs.

How it holds together

The folder is the catalog. createServiceCatalog() calls readdirSync(dir).filter(name => name.endsWith('.js')).sort() on creation — there is no index file, no database, no registration step. Adding a service is dropping a file; deleting the file removes the service on the next scan; POST /api/services/reload re-scans without a restart. The directory defaults to ./services (resolved against the working directory) and can be moved with --dir or SERVICES_DIR.

A service file is DATA, and the loader treats it that way. It is never imported. loadServiceText() walks a ladder: comments may lead but the text must then assign exactly one module.exports = <literal>; a text token gate refuses ${, require(, import(, globalThis, eval(, Function(, process.env and child_process; the surviving text is run in an empty vm context — no require, no process, code generation off, a 2 s timeout — and the loaded value is then walked for function, symbol, bigint and cycle values, each refused with the path that carried it ($.hand). Files over 2 MB are refused before they are even read. The reason is a ruling, not taste: a service file may arrive from another node, and a file that runs on receipt is a remote code path. Heavy things travel by link (models[] carry a path, url and sha256), small images ride inline as base64, and the two pages ride as strings.

A bad file is a refusal, not an outage. Every entry carries ok, errors and warnings; refusals() lists the broken ones with their reason, and GET /api/services/validate reports all of them plus whether the whole catalog is sound. One malformed file never empties the list. Duplicate names are refused on both sides — two files claiming resize both become refusals, because a name has to mean one thing, and picking a winner silently would make the catalog lie about which file it served.

The definition is an elaborate object, and that is the point. One service declares:

fieldwhat it settles
advertwhat it does, an expected time (from history — unknown stays unknown), a karma weight
providerthe app that runs it, with launch and probe — the app lives inside the definition, not beside it
variablesinit (install-time facts), input (per request), files (slots that plug a file or a service that produces one)
modesone service, several fits — each with its own models, needs, karma and install.pins (python/cuda/torch combos, sm notes for old cards)
needswhat the Resource Manager would book: gpu, vramGb, ramMb, cores, diskGb, child services
output · childrenwhat comes out; child services declared by name, wired by their outputs
pagesthe two pages the service produces: ad (sell sheet) and inputs (the way in, which also carries progress during a run)
progress · guihow a run's progress can be seen, and the service's own GUI when it has one — declared here, tracked elsewhere

The listing carries shapes; contents only ever answer a get. summarizeService() emits name, what, provider, mode names, the highest karma weight across advert and modes, the output kind, a child count, ok and the file path. It never includes pages — the gate asserts that a listing cannot contain the ad HTML. A catalog browsed by an agent has to stay cheap to read; the sell sheet is fetched per service, by name.

Modes exist so a smaller machine is not a second-class one. A mode is the fit between a service and a card: { vramGbMin: '6', sm: '<=52' } with its own model links and its own install pins. The version dance — which python, which cuda, which torch still has a wheel for an old sm_XX — lives there rather than in prose, so an installer can follow it and a reader can see why the same service has two shapes. A mode with no install and no service-level install is a warning, not an error: the installer would have to guess, and the page says so.

Karma is a weight, not a score. advert.karma and per-mode karma are numbers ≥ 0; the listing reports the maximum. Nothing in this module spends it — the ledger and the priority decision live elsewhere. Declaring it here is what lets a caller rank without re-reading every file.

Reserved words. Under /api/services/, reload and validate are routes before they are names, so a service cannot shadow them. The route matcher resolves /ad and /inputs suffixes first, then treats the remainder as a service name.

One implementation, three faces. The page at /, the JSON API under /api/ and the MCP registry at /mcp all read the same catalog object, so they cannot disagree. The MCP registry (services_list, services_get, services_ad, services_inputs, services_reload, services_validate) is the same object the module hands over for a future Api_Root mount. An optional token (SERVICES_TOKEN / --token) guards /api/* and /mcp via x-services-token or ?token=; static files are not actions and are served without it.

Who actually calls it, as of this build: Menu (renders ad and inputs pages, posts runs to the Scheduler), Join (reads the offered population from :8128), Basic_App (servicesUrl), Core (the catalog behind its advertised services), and the Scheduler's local runner (a service's definition, its port and its gui).

This is wiring in words, not a type. The shapes live in public/ts/serviceSchema.ts, serviceFile.ts, serviceCatalog.ts and apiServer.ts; if this page and those files disagree, the files are right and this page is a bug.
