FirstRun

Summary

What happens the first time Hydra meets a machine. It reads the box, proposes, and writes - it does not guess and it does not install anything the machine cannot carry. Four questions, in order: is there already an agent here? (if yes it is adopted, and it simply learns that in Hydra its name is Echidna), which brain can answer? (probed with one real call before it is trusted), which services fit? (the library's declared needs against this machine's measured hardware), and is this machine already born? (an existing node.json is refused, not overwritten).

Concepts

Adopt, do not duplicate

The operator's rule: "have your own agent installing? Ok that is Echidna! No agent? Hermes!" So /api/scan looks for agents a person may already run - Hermes, Claude Code, Codex, Aider, Gemini CLI - and the first one found is the candidate. Nothing is installed in that case. The personality file is the mechanism: it says the name, voice and tone this node calls its agent, so an adopted agent is not asked to pretend, it is told what it is called here.

A brain is not a brain until it answers

POST /api/probe-brain makes one real call and reports what came back. A candidate with no key reports reachable: true, error: "no key" plus the free models it can see - honest about being one account away from working, rather than pretending to be configured. A model that cannot answer is never written as the chosen brain.

"Mostly not enough resources" is a list, not a feeling

Every entry in the service library declares needs (gpu, vramGb, ramMb, cores, diskGb). /api/plan compares each with the machine's measured hardware - taken from ResourceManager's inventory, which resolves VRAM from the registry rather than the 32-bit AdapterRAM field - and marks it fits or does-not-fit with the reason.

Born once

Writing node.json is the moment a machine becomes a node. A second birth would silently rewrite identity, so it refuses unless the caller passes force. The reply names the ref and name it found instead.

Wiring

Doors. GET /api/doors reads every module/<name>/join.json and reports what this node is made of, with three separate states that used to be one: listening (something is there), mine (the health answer names this module) and verified. A port that answers as another module is occupiedBy, never "up" — that distinction found StateFromFile declaring 8152 while the LAN scheduler owned it, and AppPlug declaring 8156 while the LAN cycle owned that. POST /api/doors/start starts the requested doors through ProcessWrapper in dependency order and skips anything already listening, because restarting a live State door costs every publisher its entries for a cycle.
