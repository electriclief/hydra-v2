Electron_Wrapper

generic window shell — tabs, menus, tray, and the events that come back out

Electron_Wrapper is the piece of an app that owns the window. It is not an application: it is a module you load inside some other Electron main process, and it gives that process one window with a tab strip, a native menu bar, a tray, and a small event channel out. The compiled shell never needs updating, because tabs and menus are registered at run time and the window is told to redraw. It knows nothing about Hydra: it maps an address to a pane and a label to a menu item, which is why the same module is also its own demo app.

How it holds together

Everything is a registration. A tab is {type:'tab', name, path, spot?, closable?} where path is an address — host:port is completed to http://, a full URL is used as-is. A menu is {type:'menu', id, label, items[]}, and each item is {label, enabled?, checked?, type?, submenu?, onClick} — the description of a native menu, not a live object. The registry holds both, keyed by kind and key, so registering the same name twice is an update, not a second tab.

The page in the window is dumb on purpose. It subscribes, sends ew:ready, and receives one ew:bootstrap carrying {template, panes, layout, window}; after that any change arrives as ew:panes. A pane is a view of a tab: {name, title, url, visual, closable, spot}. visual is how a tab looks when nothing is wrong with it — solid, highlighted or flashing — and it is a CSS class, not a colour, so the theme stays in the stylesheet. The renderer bundles a layout engine that draws the strip and one iframe per pane; contextIsolation is on and nodeIntegration is off, with the only bridge being window.ElectronWrapperBridge from public/preload.cjs.

Closing a tab is an event, not a disposal. The renderer sends ew:event {kind:'tab-close', name}, the module unregisters that tab so the host's own state and the window agree, and then dispatches the event to the sink the host supplied. The host decides what "closed" means; the wrapper only guarantees the two sides are told the same thing in the same order.

The window is a viewer. It never owns a process, never reads a database, and never decides whether a service is up — it renders whatever address it was handed. A tab pointing at a dead door is a blank frame, and that is honest: the frame is not the service.

The template is the shape of the glass: defaultSpot names the pane region every tab lands in unless it asks for another by spot. That is the one place layout is allowed to be creative, and it is data in the caller's options rather than a setting inside this module.

Used from a host, the whole setup is a handful of lines:

const wrapper = await createModule({
  window: { title: 'Hydra V2', width: 1200, height: 800 },
  template: { defaultSpot: 'main', spots: [{ id: 'main', title: 'Main' }] },
  entries: [{ type: 'tab', name: 'Menu', path: 'localhost:8133' }],
});
await wrapper.whenBooted;
wrapper.register({ type: 'menu', id: 'view', label: 'View', items: [{ label: 'Basic', onClick() {} }] });

Contract

Files: Electron_Wrapper_module.js (the one file loaded), public/preload.cjs (the only bridge), public/index.html + public/js/renderer.js (the page and its layout engine), public/js/main/wrapperMain.js (window, menus, tray, IPC), public/js/core/{registry,menuTree,template,trayModel,statePull}.js. The module ships a runnable demo (npm start) and headless tests against a fake electron. If this page and the code disagree, the code is right and this page is a bug.
