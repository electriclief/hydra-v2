State from File

the snapshot reader · door on :8152 · replays one file into a registry

A node that boots into an empty room — no peers answering, a registry that has just started — can be handed the phone book back: one snapshot file, replayed into State as registrations, so the pointer table exists before the first peer answers. It is the other half of State to File, and it is deliberately a separate door: writing and replaying carry different risks, and a node may run one without the other.

Four rules that keep it a seed, not a truth

rulewhy
a replay never deletes and never overwrites a live ownerthe registry wins the moment its owner publishes again
a live owner's values are skipped, its link is kepta replayed heartbeat would be a fabricated "alive"; a replayed address is exactly what a reader needs
root.* is skipped unless --replay-claimsholding the root is earned by booting and renewing a lease, never inherited from a file
a torn or missing file is ok:false with the pathan empty answer reads as "nothing to do" and hides the problem

"Live" is measured, not assumed: the reader looks for node.<ref>.cycle in the target registry, which is the same signal every other reader uses.
