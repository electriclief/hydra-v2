Contract

Summary

The vocabulary every wrapper speaks to State. A wrapper is anything that runs work for Hydra - a ProcessWrapper row, an EchidnaAccess job, an idle-service guard, a miner launcher, a watchdog. Each one answers the same four questions in the same shape, so Phoenix can act on a failure without reading prose and the Menu can show it without special cases:

  1. what are you doing? - state (starting, running, idle, blocked, failed, stopped)
  2. what went wrong? - error.code from a fixed vocabulary, not a sentence
  3. can you be fixed? - fix: the declared remedy, one of four kinds, or none
  4. who must know? - needs_human when a declared fix did not work

Concepts

The entry: agent.<ref>.<wrapper>

Published into the node's own State (:8127) and republished on a cadence, exactly like every other branch. "State boots blank and persists nothing" - an entry lives as long as its wrapper; a dead wrapper is a stale entry, which is itself the signal.

{
  "ref": "xpsw",
  "wrapper": "standby-miner",
  "owner": "idle-service",            // the module that owns this wrapper
  "host": "DESKTOP-OIE507H",
  "tier": "node",                     // node | lan | global: same shape at every rung
  "state": "running",                 // starting | running | idle | blocked | failed | stopped
  "at": "2026-11-15T12:20:31-05:00",  // last heartbeat
  "lastOkAt": "2026-11-15T12:20:31-05:00",
  "pid": 8124,
  "restarts": 1,                      // how many times this wrapper has already come back
  "error": null,                      // or { code, message, at, retryable }
  "fix": { "pw": { "name": "standby-miner" } },   // what WOULD fix it - declared, never invented
  "needs_human": false                // true once the declared fix has been tried and failed
}

The error vocabulary (fixed)

Codes exist so a machine can route a failure. A wrapper that cannot pick one is reporting something nobody planned for, and UNKNOWN is the honest answer - it escalates immediately rather than being retried forever.

POOL_UNREACHABLE   DEVICE_MISSING   EXE_MISSING      CONFIG_INVALID
API_SILENT         AUTH_DENIED      PORT_IN_USE      CRASHED
TIMEOUT            DEPENDENCY_DOWN  AGENT_SILENT     UNKNOWN

Each error also carries retryable: true means "a restart may help", false means "a person must change something first" (missing GPU, wrong wallet, dead pool). Phoenix never repairs a non-retryable error - it escalates.

The four fix kinds

Phoenix may only execute what the entry declares. There is no shell kind on purpose: an automation that invents commands is a second operator.

kindshapewhat it does
http{ "http": "http://...", "method": "POST", "body": {} }a door or endpoint that knows how to repair itself
pw{ "pw": { "name": "standby-miner", "url": "http://127.0.0.1:8125" } }restart a ProcessWrapper row (locally or on a peer's own wrapper)
agent{ "agent": { "node": "richard", "cmd": "schtasks /run /tn \"hydra-mine-gpu\"" } }one declared command through Access on that node
task{ "task": { "node": "xpsw", "name": "EchidnaAccess" } }start a scheduled task on that node

The rungs

wrapper                publishes agent.<ref>.<wrapper> with error + declared fix
   |
Phoenix cycle          check fails -> run the declared fix once -> re-check
   |                     ok      -> outcome "repaired" (a receipt, not a page)
   |                     failed  -> error travels with the receipt, wrapper marked needs_human
   |
Echidna / Tell Mom     one alert naming the node, the wrapper, the code and what was already tried
   |
Menu                   the node's headline turns red and says the code; the full detail stays in the receipt
