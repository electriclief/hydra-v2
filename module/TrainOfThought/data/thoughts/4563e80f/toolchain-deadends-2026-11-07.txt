# Four ways to build sm_52 on .134, and where each one stopped (2026-11-07 14:05-14:40Z)

Box: DESKTOP-Q8U0BTH — GTX 980 Ti 6 GB / CC 5.2, driver 582.66, 4 cores, 7.9 GB RAM, 23.7 GB pagefile.
Installed: CUDA toolkit 12.4 (nvcc 12.4.131), VS 18 Community (cl 19.51.36256), VS 2022 BuildTools
(MSVC 14.39.33519 complete, 14.44 dir is a stub with only Auxiliary), SDK 10.0.22621 + 10.0.26100, no clang-cl.

The tiny probe compiled in every attempt: test-sm52.cu = one __global__ kernel + cudaMalloc/cudaMemcpy.

| # | nvcc | host cl | result |
|---|------|---------|--------|
| 1 | 12.4 | 19.51 (VS18) | `nvcc error : 'cudafe++' died with status 0xC0000005 (ACCESS_VIOLATION)` |
| 2 | 12.4 | 19.39 (BuildTools, VsDevCmd -vcvars_ver=14.39) | `nvcc fatal : Host compiler targets unsupported OS.` |
| 3 | 12.9.86 (installed for this) | 19.39 | same `Host compiler targets unsupported OS`, even with `-allow-unsupported-compiler`, and with `-std=c++17` / `-std=c++20` |
| 4 | 12.9.86 | 19.51 | `cudafe++` 0xC0000005 again |

Not the language: en-US system, en-US cl banner (VSLANG=1033 forced anyway).
Not the compiler: `cl /nologo t.cpp` in the same env compiles a <cstdio> program, exit 0.
Not the SDK: same failure with `-winsdk=10.0.22621.0`.
Not the arch: nvcc accepts `-arch=sm_52` (warns it is deprecated, then proceeds).

So the wall is nvcc's host-compiler handshake on this box: with 19.39 it decides the target OS is unsupported,
with 19.51 it gets past that and NVIDIA's own parser crashes on the newer STL headers. Both toolkits behave the
same way, so this is not "install a newer CUDA".

## The exact handshake, from nvcc -v on the first configure attempt (CUDA 12.4 + cl 19.51)
  cl.exe -D__NV_NO_HOST_COMPILER_CHECK=1 -E -TP -EHsc -D__CUDACC__ -D__NVCC__ ... CMakeCUDACompilerId.cu  > tmp/....cpp4.ii
  cudafe++ --ms_c++14 --microsoft_version=1951 --msvc_target_version=1951
           --compiler_bindir "C:/Program Files/Microsoft Visual Studio/18/Community/VC/Tools/MSVC/14.51.36231/bin/HostX64/x64/../../../../../../.."
           --sdk_dir "C:/Program Files (x86)/Windows Kits/10/" ... tmp/....cpp4.ii
  nvcc error : 'cudafe++' died with status 0xC0000005 (ACCESS_VIOLATION)

So nvcc reads the host compiler version as 19.51 and hands it to cudafe++ as --microsoft_version=1951; NVIDIA's
parser then dies on the preprocessed 19.51 headers. With 19.39 the version handshake instead fails one step
earlier ("targets unsupported OS", and -D__NV_NO_HOST_COMPILER_CHECK=1 does not suppress it). The pairing that
could satisfy both halves is an MSVC the toolkit knows AND whose headers cudafe++ can parse: 14.44.
