Event_Handler

the generic bus · own door on :8126 (not wired at boot) · loaded as a file into someone else's thread

Event_Handler is where a name becomes an action. A host registers named events, any hand fires one by name, and every firing — plus its outcome, success or throw — lands as a line in one rolling log that records who fired it. The same path serves a person's click and an agent's call, so the log is the only place either of them can be checked against the other.

How it holds together

Registering is the only way an event exists. register(name, handler, {description}) puts a name on the palette and makes its handler the action; there is no wildcard, no prefix match, no "default handler". Names are letters, digits, ., _, - and spaces, 1–64 characters, and .result / .error are refused because those two suffixes belong to the wrap. Duplicates are refused too — one name, one handler, so a trigger can never be ambiguous about what it did.

Trigger never waits. trigger(name, payload, {source}) writes the trigger line, bumps the counters and returns a receipt immediately; the handler runs on a microtask after that. Whatever it returns is written as its own line <name>.result with of pointing back at the trigger; whatever it throws becomes <name>.error with the message. That wrap is the whole design: a slow handler cannot block the caller, a throwing handler cannot lose the record, and "did it work" is answerable from the file rather than from a promise nobody kept.

Source is who fired it, and it is copied, not judged. The log line is {t, name, source, payload?, of?, result?, error?}. The class defaults source to process; the HTTP door defaults it to user and only accepts user · agent · process · system; Basic_App's adapter passes system. The class itself writes whatever string it is handed — ProcessWrapper's drain watch passes system-watch, so a log can hold a source the four-value type does not name, and the GUI's source filter cannot select it. Read the field, do not assume the enum.

One rolling file, kept small by itself. data/events.log is JSONL, appended one line at a time; the store trims lines older than retentionHours (default 24) and then, if still over maxBytes (default 8 MiB), drops oldest-first — the rewrite is atomic (temp file + rename), so a reader never sees half a log. The self-trim runs on a timer (default every 10 minutes) as well as on POST /api/events/purge, which means the file's size is a policy, not an accident, and nobody has to remember to clean it.

History is a query; live is a subscription — and they are different things. GET /api/events/log?limit=&sinceHours=&name=&source= reads the file and answers {matched, fileBytes, lines} (default 200 lines, capped at 5000). GET /api/events/stream is SSE and fans out from in-memory watchers, so a subscriber sees what happens while it is connected and nothing that happened before; a : beat every 15 s keeps the connection honest. A page that wants both loads the file once and then opens the stream — that is exactly what the GUI does.

The module is a file first and a service second. Event_Handler_module.js exports createModule({logPath}) → {handler, registry, logPath} and startModule({port}) → the same plus an HTTP door. That is how it is actually used: ProcessWrapper imports the embed file by relative path (../../../Event_Handler/Event_Handler_module.js) so the bus runs inside the wrapper's own thread with the wrapper's log path, and Basic_App's Electron main loads it through loadShelf, registering unknown names on first fire. Its own port 8126 (wiredAtBoot: false in join.json) is the module's standalone life — the same code with a door for a test, a tool, or a box that wants to watch the bus from outside.

Nothing here knows a project word. The three events ProcessWrapper registers, the four MCP tools, the four sources: all generic. The module holds no opinion about what an event means, which is why the same file can be the wrapper's console palette and an app's own event sink without a fork.
