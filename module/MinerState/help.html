MinerState

hashes and shares into Hydra State · door on :8145 · publishes node.<ref>.miner

A mining node has no Hydra shelf and does not need one: it runs a miner, and the miner publishes its own JSON on an API port. MinerState is the adapter between those two facts. It reads each declared node's miner API every fifteen seconds, normalises the answer, and registers node.<ref>.miner in State — the same place every other node publishes its own node.<ref>.*. Mirror already reads State, the Menu reads Mirror, so a share count becomes a fleet question instead of a terminal command on a slow box.

An unreadable miner is not a miner at zero

When nothing answers, State gets {readable:false, why:"no miner answering on 192.168.1.147:60130"}, never hashrate: 0. A zero reads as "mining fine, earning nothing" and hides the one fault this door exists to surface. The same rule applies to a miner that answers with a shape nobody declared: the reading is refused with the keys it did see, rather than fabricated.

A parser written for one reports zeros for the other while the card hashes at full rate — which is worse than no reading at all.

Loopback is normal, so there are two ways to read

unMiner's bundled SRBMiner binds its API to the node's loopback, so a direct fetch from this door can fail while the miner is healthy. The fallback is the EchidnaAccess agent on that node: POST /exec running (Invoke-WebRequest http://127.0.0.1:<api>/) on the box itself. Each reading records which way it was obtained (via:"direct" | "agent"), because "I could not read it" and "it is not mining" are different statements.

Share deltas, not just a rate

Every change in accepted or rejected is appended to data/miner-state.log as its own line. A hashrate never shows a rejection: a miner pointed at a pool that refuses everything looks identical to one earning, until the counter is read line by line.
