SessionDiary

the Hermes session wrapper · door on :8134 · not wired at boot · a static site first, an API for the verbs

SessionDiary turns Hermes' session store into something a human can read by double-clicking a file: one page per session saying what was asked, what actually ran, what changed on disk and where it ended. Reading needs no server. The door on :8134 exists for the four things a page cannot do by itself — rebuild the site, write a prose diary through the agent, ask a finished session a question, and fork or restart it.

How it holds together

There is one source of truth and this module does not own it. Everything on a page is derived from state.db — %LOCALAPPDATA%\hermes\state.db by default, overridable with --db or SESSIONDIARY_DB. Reads open that file with readOnly: true; the store is WAL, so the diary reads while Hermes writes and never takes a lock. Writes are narrow and named: fork — the only one the door exposes — copies a session row and its visible transcript in a single transaction, after a VACUUM INTO backup into data/backups/state-<stamp>.db (reused if younger than an hour). The store class also carries setTitle(), which no route calls. If the read-back comparison fails — message count, first and last message bytes, parent link, title — the whole fork rolls back.

A session becomes a ref, and the ref is the address everywhere. refFor() strips a local- prefix and keeps the first 8 hex characters, hashing the id when it is not hex. That is why a page is called site/session_5a5525ad.html and why the same 8-hex string can be pasted into TrainOfThought without translation. Collisions are not allowed to silently overwrite a page: when two sessions share a ref, both are extended to 10 characters and build.json counts the collision.

The site is files, not a service. site/read_dir_indexer.html is the index, site/session_<ref>.html is one page per session, site/custom.css and site/custom.js are the only shared assets, and every page carries its own JSON inline — so file:// and http:// render identically with no fetch. Alongside them the build writes the machine-readable copies: site/data/index.json (every row), site/data/sessions/<ref>.json (lean facts, no HTML) and site/data/build.json (the last build report). The site is roughly 460 files and 17 MB, so the writer skips any file whose bytes it already wrote this process, and an idle session's page is byte-identical between scans.

Two layers of prose, and the cheap one always exists. The deterministic card is written for every session on every build, for free: goal (the first real user turn, with Hermes' injected compaction and handoff turns skipped), outcome (the last assistant turn), duration, turns, tokens, cost, files touched and commands run, all scraped from tool arguments, plus the transcript with tool output trimmed. The LLM diary is a separate, optional record of 4–7 sentences in data/diaries.json, keyed by session id, written by shelling out to hermes chat --query-file <prompt> --oneshot -Q. A page shows the diary when one exists and the card otherwise; the site never depends on a model being reachable.

Asking a dead session is the same seam, with a different prompt. A seance is one question and one answer stored in data/diaries.json under seances[], with the timestamp, milliseconds, and spawnSessionId of the Hermes session that answered — because each spawn mints its own session with source oneshot, and those are hidden from the index unless you ask for them. The prompt tells the agent to read the target session with its own session_search tool and answer from that transcript only. Both paths return the command's stdout; nothing here synthesises an answer. Prompts are left behind in data/prompts/ (diary-*.txt, ask-*.txt) so a bad answer can be traced to the question that produced it.

Restart is a real terminal, not a simulation. It writes data/launch/resume-<ref>.cmd containing hermes --resume <id> and launches cmd.exe /c start cmd.exe /k <launcher>, so a path with spaces needs no nested quoting. Fork is /branch done against the store instead of a live session: a new row with parent_session_id set, title <title> (fork), counters reset, transcript copied row by row, then verified.

Links are read, never invented. At session start, TrainOfThought's scripts/session-start.mjs appends one JSONL line — {at, sessionId, refs[], note} — to data/session-links.jsonl. This module only reads that file. A missing file means no session has announced anything yet, which is a normal empty answer, not an error; every session row then simply carries no serving refs.
