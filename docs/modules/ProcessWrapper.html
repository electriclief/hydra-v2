ProcessWrapper

the process supervisor · door on :8125 · one table, one file per life, one console window at /window.html

ProcessWrapper is the only place on this box where a process may begin. It launches any command as a child, gives that child a row in one table and a text file of its own, and copies what the child said back out through the same port that launched it. Its console page at /window.html gives each running thing a tab, so watching a process and starting one are the same window.

How it holds together

One table is the truth. Everything that spawns goes through wrapper.launch(spec) and becomes one ProcessRecord: id, name, tag, command, args, cwd, shell, pid, life, spawnedAt, endedAt, exitCode, signal, chars{stdout,stderr}, truncated, streamFile. life is one of starting · running · exited · killed · failed, and a life is over when it reaches one of the last three. The law written at the top of processWrapper.ts is nothing hidden: a child is only ever created here, and it is always in the list — which is why the API, the stream fan-out, the console window and the saved commands all read the same table instead of keeping one each.

One life = one file. A launch writes an empty data/streams/<slug>-<seq>-<hex>.log — the id is the name slugged to 18 chars, a zero-padded counter and four hex digits — and every chunk is appended to it as it arrives, both channels interleaved in arrival order. The file is never rotated, is whole while the process lives, and is kept at death until an operator deletes it. The RAM buffer (bufferLimitChars, default 4,000,000) exists only for fast copies; when it has to shed old chunks it sets truncated: true rather than pretending the text is complete.

Two ways to read the same text, and the offsets are the contract. GET /api/processes/<id>/output?from=&limit=&channel= returns a copy as text/plain with the frame written into headers — x-pw-from, x-pw-to, x-pw-total, x-pw-complete — so a reader can ask again from exactly where it stopped. GET /api/processes/<id>/stream is the same content as SSE, one chunk event carrying {seq, channel, from, fileFrom, at, text}, plus open, drop and end. Offsets are character offsets in two different frames on purpose: from is inside its own channel, fileFrom is inside the life file. A slow client is told so (drop) instead of being silently skipped.

The root is a row too. The process that keeps this law for everyone else used to be the one process it did not cover — a bare console with no name, no pid, no file. captureRootLife tees the root's own stdout/stderr into streams/root.log, publishes a root record beside the children in GET /api/processes, and serves it at GET /api/root/output. It tees; it never replaces, because hiding output from a live terminal to satisfy a file would be the same mistake in the other direction. The console window is therefore no longer load-bearing, and the box can run with one window instead of a stray console beside it.

Events are the handle; the window is a view. consoleEvents.ts loads the sibling module's embed entry (../../../Event_Handler/Event_Handler_module.js) into this thread and registers three events: add Process Console Display, kill Process Console Display and note System Drain. The add event launches through the same wrapper with tag: 'console' — provider.launch is the command, command wins over it, and anything the registration supplied rides back in the result instead of being dropped. So a click, a curl, a script and an agent all take one path. /window.html polls GET /api/processes and derives its tabs from that table: every console appears as a tab, minimizing parks it without ending the process, and closing a live tab fires the kill event. A display can leave the strip while its process lives.

Saved commands are a file, not a database. data.yaml holds {name, command, args, cwd, env, shell, description, tag, createdAt, updatedAt}, written by registryStore.ts; hand edits survive the round trip, and the wrapper never rewrites a part of the file it does not own. POST /api/processes {"saved":"tick"} resolves the definition to a spec, so the thing that was tested by hand is the thing that runs later.

A token guards actions, not the page. /api/*, /health and /mcp require x-pw-token (or ?token=) when the door was started with --token; static files never do — an operator has to be able to load the GUI in order to type the token into it. POST /api/stop is the stop-all: it answers 202 first and only then takes the door down, so a caller is never left hanging on the death it asked for.
