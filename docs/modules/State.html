State

the generic retainer · door on :8127 · holds what it is handed · persists nothing

State is a registry with no opinion about what it holds. Anything — a counter, a rolling log, another module's whole registry — is registered under a dotted-path name and pulled back later, either whole or as just the part past the mark the caller carries. It boots blank, writes nothing to disk, runs no clocks and remembers nobody: an entry lives exactly as long as the thing that registered it.

How it holds together

A name is a path, and the tree falls out of the string. Registering node.123.services.llama-chat creates no parents and requires none: the dotted segments are the address, and a tree is what you get when you read them together. The same reason makes reads cheap — a pull tries the exact path, then the shortest unique suffix, so llama-chat alone resolves while it is the only one. Two matches are refused as ambiguous, and the refusal carries both full paths, because guessing between them would be the registry deciding something.

The requester carries the mark, and that is why there are no sessions. State never tracks who has read what. Instead an element can be flagged serving: { log: 'delta' }, and a pull that arrives with marks: { log: 812 } gets only what came after line 812 — a string slices by lines, an array by items, so the mark is always a plain position count. A mark that is new, unknown, stale, or unintelligible is not an error: it gets the full value plus a fresh mark. That fallback is what makes a client that has been offline for an hour correct without a repair path, and it is why State needs no clock — refresh speed is negotiated between the source and the requester, and this module sits in neither seat.

Entries describe themselves. A registration may also carry alive (a lazy liveness check), pull (a recipe the entry answers with, for live sources and relays), render and update. State calls the first on every walk and the second when asked; it stores the last two and hands them back untouched. Nothing in this module knows what a service, a node or a schedule is — that vocabulary belongs to the registrants.

A registration lives as long as its registrant. If a declared alive returns false, or throws, the entry is popped on the next walk and a dropped event is emitted with reason: 'gone'. drop(name) is the explicit hand, with reason: 'explicit'. There is no lease, no expiry and no sweep: a dead node's branch is simply not there, so absence reads as absence and the purge path a push design would need does not exist.

Contents are pulled, never embedded. discover() answers with the shape — the top-level keys, when it landed, whether it answers pulls itself, which elements are delta-served — and never with the values. A listing that carried contents would become a cache, and a cache of a live thing is a lie with a delay on it.

Nesting is registration, not knowledge. Register an object that has its own pull(name, options) method and the entry becomes a door: the parent asks it for the entry's own leaf and passes the answer up. A recipe can do the same explicitly by returning shaped(content, { full, marks }). Separately, an entry of the form { kind: 'link', to: 'http://…' } lets a pull for a name that is not here be asked of the registry at to — longest matching prefix wins, the walked bases ride along in via, a base already walked is refused rather than followed again, and the whole chase is capped at 3 hops of 900 ms each. Replies are clones, so a caller that mutates an answer cannot reach back into the registry.

Wiring, for humans

State needs nothing but a registrant. That is not modesty — it is the property that lets Core, Menu and anything else publish into it without State learning their names.

Refusals are JSON with a real code: bad_json and bad_name at 400, no_such_entry and no_route at 404, ambiguous at 409 (candidates in the message), unauthorized at 401 — and a token guards /api/* and /mcp only, since a static file is not an action. Over the wire a registration can carry content, serving, render and update; alive and pull are functions and therefore exist only for in-process registrants.
