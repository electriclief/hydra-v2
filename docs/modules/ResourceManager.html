ResourceManager

the register · door on :8129 · reads the machine, keeps bookings, enforces nothing

ResourceManager answers two different questions and refuses to mix them. What does this node have? is a read — cpu, ram, gpus with honest VRAM, disks, declared Hydra shared folders, and the gpu-side processes nobody booked — cached for four seconds and never throwing. What is already taken? is a booking — one JSON file, one write, whole or refused whole, with the holder named so a caller knows what it is waiting for. It schedules nothing and locks nothing; it is a register that will not accept a double booking.

How it holds together

Poll and book are independent, on purpose. GET /api/resources is a pure read: asking holds nothing and remembers nothing. POST /api/book is the only write, and it is a transaction over a fresh-enough read — the request is validated, compared against the machine and against everything already held, and then either the whole booking lands or nothing does. There is no queue, no ordering, no ETA, no reservation that expires: a booking lives until someone pops or clears it. That is the operator's ruling ("no internal logic — the scheduler does the thinking") made structural: this module cannot schedule even if it wanted to.

VRAM is reported with its source, because the obvious source lies. The resolution ladder is nvidia-smi → the driver registry value HardwareInformation.qwMemorySize → AdapterRAM → unknown. On Windows, AdapterRAM is a UInt32 and caps at 4095 MB — the RX 6800 reports 4095 when it has 16384 — so a card that answers only through WMI is reported as 4 GB and everything downstream under-estimates it. Each gpu therefore carries vramSource (nvidia-smi · registry · adapterram · unknown), and a reader can weigh the claim instead of trusting the number.

What is on the gpu but not booked is information, never a rule. The read keeps a gpusObserved row: processes matching a known gpu app (llama-server, sd-cli, comfyui …), a miner (lolminer, srbminer-multi, xmrig), or a python whose command line names torch, comfy, llama, diffusers, vulkan, stable-diffusion, wan or jupyter. A miner or a llama started by hand is visible and blocks nothing — the V1 lesson was that a model started outside the runner still holds the card, and pretending otherwise makes the register useless. The register's answer to that is to show it, not to police it.

A booking is a claim on amounts, one whole gpu, and a subtree of paths. The checks are exactly these, and each produces a blocker rather than a bare refusal:

kindrulewhat it compares against
gpuone app per gpu — a name match, case-insensitiveactive bookings first, then the gpus this node actually has
coressum of held cores + requested ≤ the machine's corescpu.cores
ramsum of held MB + requested ≤ total RAMram.totalMb (not free)
disksum of held MB + requested ≤ total free across drivestotalsOf(readings).diskFreeMb

Paths are not locks; they are a promise about where you will be working. Comparison normalizes separators and case (C:\work\proj equals c:/WORK/proj) and covers the subtree in both directions: a booking on C:/work/proj collides with C:/work/proj/src/main.ts and with C:/work/proj, but C:/work/proj2 is a sibling and books fine. The assumption is deliberate — children of a folder are assumed to belong to whoever holds the folder — so two parallel agents declare the directories they work in and stop stepping on each other without anyone taking a filesystem lock.

The refusal is the useful part. A refusal answers HTTP 200 with ok:false, a code and a list of blockers; each blocker carries kind, a sentence, and heldBy ({id, service, since}) when one booking is responsible. That is the wait information: not "busy" but "booked by qwen-image-2.1 since 23:35". The code is double_booked when some of the blockers name a holder, missing_resource when none do (the node lacks the gpu, or the amounts do not add up), and invalid_book when the request itself was malformed — no service name, a negative amount, or nothing to book at all.

Two exits, and they mean slightly different things. pop is the run ending normally; clear is a human wiping a stale entry. Both move the booking from active to ended with an endedAt and an endReason. The ended list is capped at 100 (ENDED_CAP) so the file stays a register and not a log.

It degrades toward answering. If the machine read fails — no PowerShell, no nvidia-smi, a timeout — safeReads() swallows it and the amount checks are skipped; the gpu-in-booking conflict and the path checks still run, so a register-only booking is still refused on a double book. A failed write to bookings.json is caught and ignored: the in-memory register keeps turning, and the next save tries again. Every read failure becomes a line in notes[] rather than an exception, because a bookkeeper that dies on a missing drive is worse than one that says "disk unknown this poll".

What it does not do is enforce. Nothing here stops a process from taking the gpu. A booking is a record plus a refusal — voluntary all the way — and the honesty of that is the feature: the register is where agreement lives, and gpusObserved is where reality shows through when the agreement breaks.

Hydra shared folders are read, not managed. data/shares.json is a declared list of paths (strings, or {label, path}); each is reported with exists and the free/total space of the volume its drive letter falls on. No file means no shares — the register never creates one.

Basic_App is the consumer in this build: it refreshes the poll, books before a run and pops after it (BASIC_RM_URL, default http://127.0.0.1:8129). The Scheduler does not call this module yet — no reference to :8129 exists in its sources — so in this build the register is booked by the app, not by the book of jobs. The agent face is POST /mcp; an optional token (RM_TOKEN / --token) guards /api/* and /mcp via x-rm-token or ?token=, and static files stay open.

This is wiring in words, not a type. The shapes live in public/ts/resourceSchema.ts, bookingStore.ts, resourceRead.ts and apiServer.ts; if this page and those files disagree, the files are right and this page is a bug.
